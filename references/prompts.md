# 提示词库 — local-app-builder

> 用法：整段复制给智能体。`【】`内按项目实际情况替换。`{{}}`是需要 AI 输出的东西。

---

## 0. 启动指令（第 1 步，建文件夹）

```
我要做一个只供自己使用的专属工作生活 APP。
请先在【桌面 / 绝对路径】新建空文件夹【木子的APP】作为项目根目录，并在其中创建如下骨架：
docs/ src/ tests/ data/ backups/ scripts/ .gitignore README.md
所有后续生成的代码、配置、启动脚本、文档、数据文件一律放在这个文件夹内，不要写到别处。
先只建目录并告诉我结果，不要写业务代码。
```

---

## 1. 需求梳理（四段式 · 核心提示词）

```
【① 目标声明】
做一个只供自己使用的专属工作生活 APP，核心是"数据永久本地存储"。

【② 功能具象化】
包含以下模块，每个模块按真实使用动作描述，不要只写名词：
- 首页总览：展示今日计划、各模块待办汇总；新增今日计划后要同步出现在首页
- 自媒体：选题灵感 → 策划 → 制作 → 发布 → 已发布数据统计（发布后可录入播放量/点赞/涨粉）
- 开发：项目列表 → 里程碑（可标记完成）→ Bug 录入（标题、严重级别、状态、所属项目、发现时间）
- 咨询：客户档案 → 沟通记录（按时间追加）→ 客户可删除
- 健康：健身记录 + 饮食记录，需要日历化（按日期查看当天记录）
- 娱乐：游戏 / 影音 / 随手记

【③ 硬性约束】
- 数据必须永久本地存储，禁止依赖浏览器缓存或 localStorage
- 重启程序、清浏览器缓存后数据毫发无损
- 默认开启自动备份
- 不做登录、不做联网部署、不做手机端

【④ 范围管控】
第一版只做 MVP 可用版本，任何额外功能先问我，不要擅自扩展。

先输出：模块清单、每个模块的核心使用场景、每个模块需要存哪些字段（表格形式），不要写代码。
```

---

## 2. 界面设计（文字稿，先设计后编码）

```
根据上面的需求，输出完整界面架构，全部用文字描述，不要写代码：
1. 全局布局：左侧导航栏（列出全部模块入口）+ 中央内容区 + 上方工具栏（全局操作/切换）
2. 每个模块单独一段设计说明：页面有哪些区块、每个区块有哪些字段、交互动作、状态如何流转
   - 自媒体页：五步流程流（灵感→策划→制作→发布→已发布），说明如何推进阶段（点击/拖拽）
   - 开发页：里程碑标记方式 + Bug 录入表单字段
   - 健康页：日历视图如何呈现健身与饮食
3. 通用交互规范：新增/编辑/删除反馈、空状态、危险操作二次确认

输出后停下来等我确认，再进入 PRD。
```

---

## 3. PRD（施工图）

```
基于已确认的界面设计，生成 docs/PRD.md，必须覆盖六大维度：
1. 产品目标与私有化定位（只给自己用、数据不出本地）
2. 典型使用场景（至少 5 条，例如"添加今日计划 → 同步至首页总览"）
3. 完整页面结构（全局布局 + 每个模块页面的字段与区块）
4. 各模块功能定义与数据流向（实体、字段、CRUD、模块间联动关系）
5. 本地持久化与备份机制（存储位置、文件格式、备份触发时机、恢复步骤）
6. 第一版验收标准（运行稳定性 / 数据联动性 / 模块交互完整性，每条必须可判定通过与否）

另外单独一节列出【暂不实现项】：多用户权限、登录、云同步、手机端、团队协作等。
标注每个模块属于第一版必须实现，还是可延后。
写完后把 PRD 全文给我审阅，我确认后才开始写代码。
```

---

## 4. 开发计划（极简提示词）

```
根据当前 PRD 列出详细可执行开发计划。
要求：包含 9 个阶段、每个阶段的测试节点、每个阶段的交付物定义。
```

> AI 会输出它自己的任务分解表。人不用看懂技术细节，只需确认：① 计划存在 ② 阶段顺序 = 骨架 → 数据层 → 各模块 → 首页联动 → 测试 → Git → 走查 → 修复 → 美化。

---

## 5. 分阶段开发（每阶段都要注入测试）

```
按开发计划执行第 N 阶段：【阶段名】。
规则：
- 本阶段完成后立即注入对应的自动化测试并运行
- 测试必须真实运行并全部通过，禁止跳过、删减断言、注释掉测试
- 测试失败：定位 → 修复 → 重测，直到全绿
- 完成后输出：改了哪些文件、测试命令与结果、下一阶段是什么

不要提前实现后续阶段的内容。
```

---

## 6. Git 存档

```
帮我做 Git 版本控制：
1. 检查 Git 是否安装
2. 初始化仓库（如未初始化）
3. 把当前所有文件加入版本控制并提交，提交消息：完成木子工作台V1.0
4. 输出 git log 结果
```

---

## 7. 走查（真实用户视角）

```
以真实用户视角全流程走查这个 APP，逐页记录问题。
输出 docs/走查报告.md，包含：
- 每个模块的走查路径与观察到的问题
- 缺陷分级表：功能型缺陷（数据展示不全、交互缺失、UI 反模式）与视觉体验问题分开列
每条缺陷写成可执行的修复指令（明确文件/位置/期望行为）。
```

---

## 8. 二次修复（原子提交）

```
修复缺陷：【缺陷编号 + 描述】
要求：
- 只改这一条缺陷涉及的部分，不顺手改其他东西
- 改完重跑全部自动化测试，必须全绿
- 单独提交一次 Git，提交消息：【中文动宾短语，如 修复：客户档案支持删除】
- 报告：改了哪些文件、测试结果、提交 hash
```

---

## 9. UI 风格美化（三风格）

```
【第一步：风格提取】
我要的风格是：【例如 macOS 天气 APP 的毛玻璃效果】。请先描述该风格的视觉特征（层次、透明度、圆角、阴影、动效、配色、间距），形成一段可复用的设计提示词。

【第二步：注入实施】
把上面这段风格特征注入到本项目，实现【毛玻璃拟态风 / Notion 笔记风 / 新粗野主义风】。
硬性要求：
- 仅做外观变更，不改动任何功能逻辑、不改变数据结构、不改变任何已有交互行为
- 做成可切换的主题变量层，一键切换三种风格
- 完成后必须重跑全部自动化测试，必须全绿
```

---

## 10. 开源复用

```
把项目整理成可开源、可复用的形态：
1. 写 README：项目定位、模块清单、截图位占位、启动方式（双击脚本）、改造路径
2. 改造路径标准化说明：解压 → 用智能体打开文件夹 → 运行"安装依赖 + 启动项目" → 按需增删模块
3. 举例说明模块替换：健身→打球/听歌、咨询→学习/育儿、新增读书模块（书籍录入、进度统计、笔记撰写）
4. 生成完整 ZIP 包（不含 node_modules 等可再生依赖）
5. 提交到 GitHub（若已配置远端），或给出待推送的远端信息
```

---

## 11. 启动脚本交付

```
生成可直接双击运行的启动脚本：
- Windows: scripts/start.bat
- macOS: scripts/start.command（并设置可执行权限）
- Linux: scripts/start.sh
行为：检查运行环境 → 安装依赖 → 启动本地 Web 服务 → 自动打开浏览器 → 打印访问地址 → 失败时给出可读错误原因。
完成后请真实运行一次验证能起服务并返回页面内容。
```
